\begin{abstract}
We ask whether a repository \emph{context engine}---a retrieval stack that indexes a codebase and returns files to a coding agent---improves on what a practitioner would assemble from standard parts, and whether it changes what the agent repairs. Published margins are typically measured against weak lexical baselines, on evaluation sets development had already seen, and across engines whose output contracts differ. We evaluate one open-source engine, \system{}, under a protocol that records for every evaluation case whether development could have seen it, compares against a ladder of conventional retrievers built from the same embedding model with \system{}'s own rerankers and expansion attached and then varies candidate generation and reranking factorially, matches output contracts across two hosted engines through one frozen synthesis stage, and runs a preregistered executable pilot on the ranking evaluation's own tasks. On 160 SWE-bench Verified localization instances never seen by development, \system{} leads the full conventional stack by $+0.06$--$0.08$ on Recall@5, Recall@20, and budget-constrained yield (repository-cluster $95\%$ intervals excluding zero; MRR tied); on an 18-case repository-disjoint commit-to-files set the conventional stack leads. The ladder's increments are heterogeneous: on issue queries the shared reranking head is the largest conditional gain ($+0.29$ to $+0.34$ MRR on conventional candidates), on commit-to-files queries it adds nothing ($+0.004$), and the factorial locates \system{}'s own contribution on issue queries in its candidate pool ($+0.19$ MRR, $+0.07$ Recall@20 before any reranking), most of whose MRR advantage the shared reranker recovers for the conventional candidates. Under matched contracts the documentation engines are statistically indistinguishable at $n{=}40$; the hosted synthesis engine's cited-source sets repeat exactly while \system{}'s retrieved chunks repeat in $98\%$ of pairs in-process, though re-indexing a corpus from scratch reproduced its ordered top-20 on only 1 of 18 cases. In the executable pilot (mini-SWE-agent, 62 instances, two trajectories each) a \system{} seed changes verified repair by $+0.048$ \ci{-0.008}{+0.113} over no seed and by $-0.008$ over random files; the seed's file heads contained an edited region in only 9 of 50 seeded gold files, and a check of three seed interfaces on the same instances leaves the effect unresolved. We release code, per-case artifacts, agent trajectories, and the exposure ledger.
\end{abstract}

\section{Introduction}

Coding agents increasingly rely on a context engine: a service that indexes a repository and, for each agent query, returns the files the agent should read. Such engines combine dense retrieval, lexical matching, structural indices, learned rerankers, and query expansion, and report large gains over lexical baselines. Those gains are hard to interpret. The evaluation cases were often available, at least in aggregate, while the engine's components were selected, so a margin partly measures selection. The baselines are usually lexical, so a margin cannot be attributed to the engine's design rather than to a learned reranker that would help any candidate pool. Comparisons with hosted engines mix output contracts and measure different quantities under one name, determinism among them. And retrieval quality is rarely connected to what an agent repairs.

We study these questions for one open-source engine, \system{} (hybrid lexical/vector candidates, query expansion, a cross-encoder, a listwise reranker), whose own history exhibits the first problem: its largest evaluation partition (220 Agent Retrieval Bench cases) was re-drawn from a pool every case of which had been scored in an earlier development round whose aggregates gated which components shipped. We ask three questions under a protocol that removes each confound.

\begin{enumerate}
    \item \textbf{RQ1 (ranking).} Against lexical baselines, a component-matched conventional hybrid, and hosted engines, where does \system{} lead, tie, or trail on cases that no development decision could see, and which of its components account for the difference?
    \item \textbf{RQ2 (determinism).} Where does run-to-run variance come from, and when the same quantity is measured for every engine, which engines are stable?
    \item \textbf{RQ3 (utility).} Holding the agent, its tools, and its budget fixed, does a retrieval seed change what the agent submits, and does it change verified repair?
\end{enumerate}

\paragraph{Contributions.}
\begin{itemize}[leftmargin=1.2em]
    \item \textbf{An exposure protocol.} A case-level ledger assigns every evaluation set one of three classes according to what development could have seen (\S\ref{sec:protocol}). Applied to \system{}, it reclassifies the 220-case ARB partition from held-out to validation evidence; confirmatory results rest on 178 cases scored once and never before (62 and 98 SWE-bench Verified instances; 18 repository-disjoint commit-to-files cases).
    \item \textbf{A component-matched baseline ladder and a factorial.} Four conventional retrievers add \system{}'s embedding model, BM25 fusion, its rerankers, and its query expansion one at a time, using \system{}'s own prompts and parsers; a candidate-generator $\times$ reranker factorial then separates the two factors the ladder confounds. On issue queries the shared reranking head is the largest conditional gain ($+0.29$ to $+0.34$ MRR on conventional candidates) and \system{}'s own contribution sits in its candidate pool ($+0.19$ MRR, $+0.07$ Recall@20 before reranking); on commit-to-files queries the reranking head adds nothing and \system{} trails (\S\ref{sec:ranking}).
    \item \textbf{Matched contracts for hosted engines.} Routing every engine's retrieved evidence---including a hosted synthesis engine's own recorded sources---through one frozen synthesis stage turns an apparent hosted lead into a four-way tie above a no-retrieval floor; measuring repeatability at each engine's observable retrieval unit shows the hosted synthesis engine's cited-source sets repeating exactly and \system{}'s retrieved chunks repeating in $98\%$ of pairs (\S\ref{sec:determinism}--\ref{sec:docs}).
    \item \textbf{A preregistered executable pilot, and an audit of its seed.} On the same 62 instances as the ranking evaluation, a fixed agent with a retrieval seed resolves no more verified repairs than with a random-file seed; two trajectories per cell disagree by more than the effects under study; the seed's file heads rarely contained the edited region; and the pilot's variance yields a precision target for a decisive study (\S\ref{sec:utility}).
\end{itemize}

We claim no state of the art; the findings are largely null or negative for the engine we built, and we report them with the same prominence as the positive ones.

\section{Related work}

SWE-bench established executable repository-level issue resolution
\citep{swebench}, while SWE-agent and Agentless expose repository navigation and
localization as explicit stages \citep{sweagent,agentless}. LocAgent studies a
graph-guided localization agent and reports that better localization can improve
multi-attempt repair \citep{locagent}. Repository-level code completion shows that cross-file retrieval matters once
the edit location is known \citep{repocoder,coderag}. Dense retrieval, late interaction, and hypothetical-document
expansion motivate the components in practical context engines
\citep{karpukhin2020,khattab2020,gao2023hyde}, while BM25 remains a strong
exact-term baseline for code \citep{bm25}.

The closest work measures context acquisition directly. ContextBench provides
human-verified file, block, and line contexts for issue-resolution tasks and
scores agent trajectories \citep{contextbench}. CORE-Bench scales
requirement-driven retrieval across code understanding, edit localization, and
broader context \citep{corebench}. SWE-Explore derives audited line-level
targets from successful trajectories \citep{sweexplore}. Agent Retrieval Bench
(ARB) contributes workflow-derived next-context targets, base-commit hygiene,
budget-aware file metrics, open-embedding and RepoMap baselines, and a
closed-tool seed intervention with no-seed, random, retrieval-derived, and
oracle arms \citep{arb}. Our closed-tool experiment (\S\ref{sec:utility}) is a
replication of that intervention with an additional seed, not a new design. What
we add is narrower: an exposure ledger, a component-matched ladder with a
factorial, matched output contracts and like-for-like determinism for hosted
engines, and a preregistered executable pilot on the ranking evaluation's own
tasks.

\section{Evaluation protocol}
\label{sec:protocol}

\paragraph{Exposure classes.} Every evaluation set is assigned a class in a case-level ledger (Appendix~\ref{app:exposure}, Figure~\ref{fig:timeline}). \textbf{C0}: never scored by any system before its single confirmatory run, drawn from a pool no development decision could see. \textbf{C1}: development. \textbf{C2}: re-partitioned from a pool whose cases were all scored in an earlier round, where that round's aggregates influenced the shipped system. The 220-case ARB partition is C2: all 427 ARB v2 cases were scored in a first development round; that round's held-out aggregates were the acceptance test for query expansion, listwise reranking, the cross-encoder blend, reciprocal-rank fusion, and the path-affinity branch (Appendix~\ref{app:development}), and its per-workflow rates motivated the quoted-path demotion fix. A second round then drew a new $25/75$ split from the same pool, excluded 50 legacy-exposed IDs, and queried the 220-case partition once. Re-drawing does not un-expose a case, and the first round's per-case outputs are not retained, so we treat the partition as validation evidence and make no confirmatory claim on it. The C0 sets are: 62 stratified SWE-bench Verified localization instances (12 repositories; leakage audit $0/62$); an 18-case commit-to-files final over a repository-disjoint corpus locked before any scoring; and 98 further Verified instances drawn under a fresh salt from the 438 no round had used (\S\ref{sec:ranking}). A 40-case DS-1000 development subset drives the documentation track and is C1. The ledger controls author exposure; it cannot control whether the foundation models inside any engine saw these public repositories during training, a caveat shared by every arm.

\paragraph{Queries, corpus, metrics.} Queries are the official ARB gold-free structured objects. File text comes from bare git clones at each case's base commit (binary and non-UTF-8 blobs skipped). Metrics are ARB's official per-case metrics (MRR, Recall@$k$) plus BCY@8k, the budget-constrained yield from packing ranked files into an 8{,}000-token context with ARB's packing routine. Documentation cases score \emph{identifier hit}: whether the returned text contains the case's gold API identifier.

\paragraph{Freeze and attestation.} All \system{} numbers come from one frozen build with exact vector scan, API $\text{top-}k{=}20$, and response-level configuration attestation: every response carries the retrieval configuration actually served, and a run aborts on the first mismatch with its declared configuration. The frozen configuration is reproduced in Appendix~\ref{app:system}. Paired deltas carry cluster bootstrap $95\%$ intervals (20{,}000 resamples, seed 1042; repository clusters for repository tracks, case clusters for documentation), plus exact McNemar tests on any-gold@20 movement.

\paragraph{Matched baseline ladder.} The lexical comparators (whole-file BM25, ARB's official lexical ranker, and their development-tuned fusion) cannot say how much of a margin is \system{}'s engineering and how much is a learned reranker on top of any candidate pool. We therefore add four conventional systems, each adding one \system{} component to the previous one, over the official ARB chunks (file chunk plus symbol chunks) of the identical corpus: \textbf{dense}, \texttt{text-embedding-3-small}---the embedding model inside \system{}---max-pooled to files; \textbf{hybrid}, reciprocal-rank fusion ($k{=}60$, equal weights, untuned) of the dense ranking and BM25; \textbf{+ rerankers}, the hybrid's top 50 narrowed to 30 through \system{}'s cross-encoder (\texttt{ms-marco-MiniLM-L-6-v2}, blend $0.4$) and then \system{}'s listwise \texttt{gpt-4o} reranker over the top 20 (seed 1042, identical prompt); \textbf{+ expansion}, the same with \system{}'s hypothetical-document expansion (\texttt{gpt-4o-mini}, identical prompt and gate) feeding the dense query. We call the last rung the \emph{full conventional stack}. Prompts and parsers are imported from \system{}'s source, so they are identical by construction (Appendix~\ref{app:ladder}). What remains between the full conventional stack and \system{} is exactly \system{}'s own contribution: exact-symbol, exact-path, path-affinity, and trigram branches; its chunker and index; tuned fusion weights; quoted-path demotion. A ladder measures \emph{conditional} increments in one construction order; when components interact it does not allocate the final score uniquely among them. We therefore also score a $2\times2$ factorial with expansion held constant: \{conventional, \system{}\} candidate generation $\times$ \{none, \system{}'s\} learned reranking, where the \system{}-candidates-without-reranking cell is the frozen build with both rerankers disabled and everything else unchanged (Appendix~\ref{app:factorial}). The factorial was scored after the confirmatory runs on the same cases; it is explanatory, and no shipped configuration was chosen on it.

\paragraph{Hosted engines.} Two commercial engines are compared on the documentation track: a \emph{documentation engine} returning raw documentation context for a library query, and a \emph{synthesis engine} returning a grounded answer with cited sources; \S\ref{sec:docs} matches their output contracts before comparing. The synthesis engine's repository surface could not be indexed at the required commits (Appendix~\ref{app:hosted}), so no repository number is reported for it in either direction.

\paragraph{Claim rule.} ``State of the art'' would require leading every directly comparable engine on a C0 set with the complete comparable engine set runnable. No result in this paper meets it.

\section{Retrieval quality under matched baselines (RQ1)}
\label{sec:ranking}

\paragraph{Against lexical baselines.} \system{} leads whole-file BM25, the official lexical ranker, and their tuned fusion on every set (Figure~\ref{fig:ladder}, Tables~\ref{tab:independent}--\ref{tab:arb}): on the independent final its Recall@20 leads over BM25 and the lexical ranker exclude zero; on SWE-bench its MRR lead over the strongest lexical system is $+0.274$ \ci{+0.194}{+0.412} with Recall@20 tied. None of this isolates \system{}'s contribution.

\paragraph{Against the matched ladder: heterogeneous increments.} The independent final (Table~\ref{tab:independent}) is the first of two clean tests. The dense rung alone, using nothing but the embedding model \system{} already calls, ties \system{} on any-gold and exceeds it on Recall@20 ($0.796$ vs.\ $0.750$). Untuned fusion with BM25 reaches MRR $0.579$ and Recall@20 $0.870$ against \system{}'s $0.508$ and $0.750$ (Recall@20 gap $-0.120$ \ci{-0.231}{-0.019}); adding \system{}'s rerankers \emph{lowers} MRR to $0.545$, and expansion raises it to $0.619$, so \system{}'s deficit against the full conventional stack ($-0.111$ \ci{-0.200}{-0.034}) excludes zero. Six repository clusters is a small basis for an interval; the point is that nothing \system{} adds on top of the conventional stack is visible here. The 62-instance SWE-bench set (Table~\ref{tab:swebench}) has a different shape. On issue text the dense rung is weak (MRR $0.254$) and untuned fusion helps little ($0.296$); attaching \system{}'s rerankers moves MRR to $0.575$ ($+0.279$) and expansion to $0.597$; \system{} then leads by $+0.083$ MRR \ci{-0.107}{+0.203}, $+0.080$ Recall@20 \ci{-0.105}{+0.217}, and $+0.065$ BCY \ci{-0.062}{+0.171}, any-gold 48 vs.\ 44 ($p{=}0.42$): a tie. The 98-instance expansion repeats this shape (rerankers $0.306\to0.611$). On the C2 ARB partition (Table~\ref{tab:arb}) the rerankers add only $+0.019$ while \system{}'s own components add $+0.103$ MRR \ci{-0.008}{+0.189} over the full conventional stack; that is the set on which those components were selected, so the margin is the expected direction of selection, not evidence (its per-workflow breakdown is a hypothesis for a designed test, Appendix~\ref{app:results}). The reranking head is therefore the largest conditional gain on issue-style queries and nothing on the commit-to-files set; the ``$+0.3$'' is a SWE-bench finding, not a property of the components.

\paragraph{Separating candidates from reranking.} The ladder cannot say whether \system{}'s margin on issue queries comes from a better candidate pool or from an interaction with the shared reranker, because it only ever adds the reranker to conventional candidates. The factorial (Figure~\ref{fig:factorial}, Appendix~\ref{app:factorial}) answers this on the expansion set. Before any learned reranking, \system{}'s candidate generator beats the conventional dense+BM25 pool by $+0.188$ MRR \ci{+0.036}{+0.317}, $+0.073$ Recall@20 \ci{+0.005}{+0.159}, and $+0.160$ BCY \ci{+0.072}{+0.310}. The shared reranking head is worth $+0.341$ MRR \ci{+0.256}{+0.468} on conventional candidates but $+0.193$ \ci{+0.161}{+0.285} on \system{}'s, so the two factors are partial substitutes: the reranker recovers most of the MRR the weaker pool had lost, and what remains is the recall it cannot manufacture ($+0.087$ Recall@20) plus a tied MRR ($+0.041$); it leaves conventional Recall@20 unchanged by construction, since it reorders a 30-candidate window. On the commit-to-files set the pattern inverts: \system{}'s candidate pool trails the conventional hybrid before any reranking ($-0.099$ MRR \ci{-0.190}{-0.028}; $-0.102$ Recall@20 \ci{-0.213}{+0.000}), and the rerankers add nothing to either pool ($+0.004$ MRR \ci{-0.093}{+0.119} on conventional candidates, $+0.065$ \ci{-0.044}{+0.176} on \system{}'s, same index); on the ARB partition they add $+0.008$ \ci{-0.011}{+0.031} to conventional candidates. The heterogeneity therefore sits in candidate generation: \system{}'s six-way tuned fusion yields more recall than two-way fusion on issue text and less on short commit messages, where the dense branch alone already reaches $0.796$ Recall@20. Which branch, weight, or rule carries this is not isolated by the design and is the next experiment.

\paragraph{Where \system{} stands.} To widen the C0 basis we drew 100 further Verified instances under a fresh salt from the 438 no round had used, applied two engine-agnostic rules before any scoring (gold files must exist at the base commit; ARB's leakage check), leaving 98, provisioned the frozen build on them after a complete index audit (Appendix~\ref{app:system}), and scored every system once (Table~\ref{tab:expansion}). \system{} finishes at $0.700$ MRR against the full conventional stack's $0.660$, with margins of $+0.041$ MRR \ci{-0.028}{+0.112}, $+0.061$ Recall@5 \ci{+0.023}{+0.148}, $+0.087$ Recall@20 \ci{+0.042}{+0.167}, and $+0.082$ BCY \ci{+0.030}{+0.152}. Pooling the 160 SWE-bench instances (Table~\ref{tab:pooled}, Figure~\ref{fig:forestfull}) gives the same reading: $+0.057$ MRR \ci{-0.036}{+0.114} with Recall@5, Recall@20, and BCY all excluding zero and any-gold 131 vs.\ 120 ($p{=}0.08$). Against the lexical ranker, which is strong at Recall@20 on issue text ($0.793$), \system{}'s pooled Recall@20 lead is a tie ($+0.030$ \ci{-0.019}{+0.117}) while its MRR and BCY leads exclude zero. The answer to RQ1 is therefore conditional on query style. On issue queries \system{}'s own additions are worth $+0.06$ to $+0.09$ on the yield metrics over a conventional stack built from its own parts, resolved at $n{=}160$, and the factorial places that value in the candidate pool; on commit-to-files queries they are worth less than nothing, resolved at $n{=}18$ with six clusters. Latencies (Table~\ref{tab:latency}) and development-time ablations (Appendix~\ref{app:development}) are in the appendix.

\section{Determinism, like for like (RQ2)}
\label{sec:determinism}

\paragraph{The pipeline was the variance.} Repeating eight ARB queries ten times against the pre-freeze stack gave a mean exact top-10 rate of $30.6\%$. Paired traces isolated uncached, unseeded LLM stages; insertion-order ties in fusion SQL; and approximate nearest-neighbour search under concurrency. Total SQL ordering, single-flight sharing of concurrent identical hosted calls, an explicit seed, and a persistent stage cache take exact repeats to $100\%$ in-process; a cold restart still moved $7/8$ lists until the cache was warm, after which $8/8$ survive two restarts. We claim restart-durable repeatability from the first persisted answer, not that two clean installations agree on their first answer, and the factorial quantified the difference: re-indexing the independent corpus from scratch and re-running the frozen configuration with an empty stage cache reproduced the ordered top-20 on 1 of 18 cases and the top-20 set on 7; Recall@20 and BCY were identical for every case, and MRR moved by $+0.072$ \ci{+0.005}{+0.159} (Appendix~\ref{app:factorial}), which is as large as several differences reported on that set. Embedding APIs were not the problem (Appendix~\ref{app:determinism}).

\paragraph{Same quantity, every engine.} A naive comparison---$98.0\%$ byte-identical context for \system{} against $35.6\%$ and $0.0\%$ for the hosted engines---compares retrieval stability for two engines with generated-text stability for the third. Table~\ref{tab:determinism} separates the layers and measures each engine at its observable retrieval unit: the synthesis engine's cited-source URL sets are identical across every pair ($1.000$); \system{}'s retrieved chunks across $98.0\%$; the documentation engine's retrieved chunks across $54\%$ (quality-guided) or $50\%$ (oracle IDs). The units differ in granularity, so these numbers do not rank the engines' underlying retrieval stability: the synthesis engine could cite the same pages while selecting different passages, which its API does not expose. What is observable is that its answer text never repeats byte-for-byte and that this flips the identifier-hit outcome in $7.1\%$ of pairs, against $0\%$ for \system{}. The defensible statements are narrow: \system{}'s caching and total ordering make its retrieved text, and hence downstream decisions, repeatable; the documentation engine's retrieval drifts at the chunk level; the synthesis engine's cited sources do not drift, its prose does.

\section{Documentation retrieval under matched output contracts}
\label{sec:docs}

Documentation retrieval is where hosted engines are strongest and where output contracts differ most. The synthesis engine returns a fluent answer with citations; the documentation engine and \system{} return raw context. Scored naively, the synthesis engine leads (identifier hit $0.575$ against \system{}'s $0.400$ and the documentation engine's $0.375$). That comparison conflates retrieval with the synthesis model's parametric knowledge.

\paragraph{Matching the contract.} Routing only the two raw-context engines through a frozen synthesis stage (\texttt{gpt-5.4-mini}, 1{,}600 output tokens, one system prompt) and comparing them with the synthesis engine's \emph{native} pass aligns the output format but not the synthesis model or prompt. The synthesis engine's raw-retrieval mode returned no sources during the recorded round, but its synthesized responses carry the five retrieved source chunks it grounded on; we reconstructed that context from the recorded responses (mean 2{,}754 tokens), packed it under the same 8{,}000-token budget with the same routine as every other arm, and routed it through the same frozen stage, three repeats, no new hosted calls. Figure~\ref{fig:docs} is a four-arm comparison under one synthesis model, one prompt, one budget.

Three findings follow. First, on raw retrieved context the synthesis engine is ahead of \system{}: its reconstructed five-source context hits the gold identifier on $0.475$ of cases against \system{}'s $0.400$ ($k{=}5$) and $0.425$ ($k{=}20$). Second, under the matched contract the four arms finish within $0.05$ of one another and every engine-versus-engine interval includes zero (Table~\ref{tab:docspairs}); the synthesis engine's matched arm ($0.583$) differs from its native pass by $+0.008$ \ci{-0.050}{+0.075}, so no difference between its own synthesis and the frozen stage is resolved on this metric. Third, the metric is near saturation: the model alone scores $0.492$ and the retrieval-over-floor differences are small ($+0.13$, $+0.13$, $+0.09$); because retrieval may help some cases and hurt others, the floor bounds the room the metric leaves rather than decomposing scores into parametric and retrieved parts. We detect no statistically resolved difference between any two engines under this evaluation; ``parity or better'' is not supported either, since an interval of \ci{-0.09}{+0.16} does not establish it, and non-inferiority would require a predeclared margin and a sample several times this size.

\section{Agent utility (RQ3)}
\label{sec:utility}

\paragraph{Two preliminary measurements.} A replication of ARB's closed-tool seed intervention (40 paired development cases per arm) finds that seeds change which files a frozen agent submits, ordered by seed quality: file-F1 rises from $0.046$ with no seed to $0.234$ with a \system{} seed ($+0.188$ \ci{0.055}{0.294}) against an oracle ceiling of $0.858$ (Appendix~\ref{app:pilot}). Executing generated code on 40 DS-1000 cases $\times$ 3 repeats leaves every retrieval arm within \ci{-0.14}{+0.20} of the no-retrieval control (Appendix~\ref{app:docs}): 40 cases cannot tell.

\paragraph{Executable pilot (preregistered).} To measure retrieval and executable outcome on the same tasks, we preregistered a pilot (Appendix~\ref{app:pilot}) on the 62 C0 SWE-bench instances whose rankings every system in Table~\ref{tab:swebench} had already produced once. The agent is mini-SWE-agent with \texttt{gpt-5.4-mini}, ordinary shell tools in every condition, and a fixed step budget; a seed is a block appended to the issue naming the top five files a recorded ranking produced, with the first 40 lines of each file, capped at 3{,}000 tokens. Conditions: no seed; five random non-gold files in the same block (prompting control); \system{}'s recorded top five; the full conventional stack's recorded top five. The outcome is verified repair under the official harness, paired by instance, with instance- and repository-cluster intervals. Every condition was run twice (two independent trajectories per instance); Figure~\ref{fig:pilot} reports both repeats and their pooled per-instance means.

The two repeats disagree by more than the effects under study, which is the first result. Resolved counts were 25/30/31/23 (none/random/\system{}/conventional) in the first repeat and 25/27/25/25 in the second; within a condition, 7--10 of 62 instances flip between repeats. Pooled, no seed effect is resolved. A \system{} seed changes the per-instance repair rate by $+0.048$ \ci{-0.008}{+0.113} against no seed, and by $-0.008$ \ci{-0.073}{+0.056} against a block of five random non-gold files, which itself sits at $+0.056$ \ci{-0.016}{+0.137} over no seed. The conventional stack's seed is the only arm that trails a comparator with an interval excluding zero ($-0.073$ \ci{-0.145}{-0.008} against the random control); we have no explanation and offer none. Budgets were not binding: agents used 7--8 of 50 steps and cost about two cents per instance.

\paragraph{What the seed contained.} Two audits qualify what the pilot tested. The seed is a \emph{file hint plus file head}, not the engine's task-relevant evidence: among the 50 gold files \system{}'s seed named, the first 40 lines covered a region the gold patch edits in only 9 (median first edited line 200). The random control excludes gold files but is not thereby uninformative: its 310 files were $30\%$ tests, $25\%$ Python sources, $15\%$ documentation, and $30\%$ other, with $1.3\%$ in the same directory as a gold file, so what it contributes is repository orientation, not the fix location. To test the interface we ran two further arms on the same 62 instances with one trajectory each (exploratory, not preregistered): \system{}'s top five as paths only, and as paths plus each file's best-matching chunk for the issue text (BM25, capped at 60 lines, same budget; it covered an edited region in 13 of the 50 seeded gold files). Paths only resolved 26 and paths plus chunks 24, against 25 with no seed and 31 and 25 in the two file-head repeats; neither interface differs from no seed ($+0.016$ \ci{-0.097}{+0.129}; $-0.016$ \ci{-0.097}{+0.065}), and the spread across interfaces is smaller than the spread between repeats of one interface (Table~\ref{tab:seedinterface}). Pooled per-instance paired differences in the pilot have standard deviations of $0.23$--$0.30$; a study on 200 instances with two trajectories each would have an expected $95\%$ half-width of about $0.04$ before repository clustering, and we set that, not a favourable interval, as the confirmatory design (Appendix~\ref{app:pilot}). At about \$11 for 496 trajectories it is affordable; what it needs first is the seed interface fixed on development tasks.

\section{Discussion and limitations}
\label{sec:claims}

\textbf{Supported.} \system{} leads lexical baselines on every set; against the full conventional stack it leads by $+0.06$--$0.08$ on Recall@5, Recall@20, and BCY over 160 pooled SWE-bench instances (MRR tied) and trails on the 18-case independent final. The ladder's increments are heterogeneous: the shared reranking head is the largest conditional gain on issue queries ($+0.28$--$0.34$ MRR) and adds nothing on commit-to-files queries or the ARB partition given expansion; on issue queries \system{}'s own contribution sits in its candidate pool ($+0.19$ MRR, $+0.07$ Recall@20 before reranking), and the reranker recovers most of the MRR but not the recall for conventional candidates; on commit-to-files queries \system{}'s candidate pool has lower recall than the conventional hybrid ($-0.10$ Recall@20) and the reranker adds nothing to either pool. Under one frozen synthesis stage no two documentation engines are statistically distinguishable at $n{=}40$. \system{}'s retrieved text is repeatable in-process and across restarts with a warm cache; the hosted synthesis engine's cited-source sets repeat exactly. Retrieval seeds change a closed-tool agent's file selection, ordered by seed quality.

\textbf{Not supported.} State of the art, anywhere; any confirmatory result on the C2 ARB partition; documentation parity or non-inferiority; downstream utility on DS-1000 at $n{=}40$ or in executable repair at $n{=}62$, in either direction; a ranking of the engines' underlying retrieval stability (the observable units differ); a decomposition of documentation scores into parametric and retrieved contributions; that the pilot's seed delivered the engine's evidence rather than file names and heads; and MRR differences on the 18-case set smaller than the $+0.07$ re-indexing shift.

\textbf{Limitations.} One engine is studied in depth; the hosted engines only where their surfaces permitted a matched measurement, and one arm is missing. The C0 sets are small (18, 62, 98) and their two query styles live in different repository collections, so query style and corpus are confounded in the heterogeneity we report. The factorial's \system{}-candidates-without-reranking cell exists only where an index could be re-provisioned, and it does not isolate which candidate branch carries the advantage. Every arm shares one embedding model and one family of foundation models, so training-set exposure of the public repositories is uncontrolled. The pilot uses a small policy model, one agent scaffold, and a seed interface that rarely carried the edited region; two trajectories per cell are too few. The documentation metric is near saturation. The ledger records what the authors could see, not what the models had seen.

\section{Conclusion}

Measured against baselines built from its own parts, and on cases its development could not see, most of \system{}'s advantage over lexical retrieval on issue-style queries is the part any careful practitioner would assemble. What is \system{}'s own is a better candidate pool on issue queries, worth $+0.19$ MRR and $+0.07$ Recall@20 before reranking and $+0.06$ to $+0.08$ on yield metrics after it, at $n{=}160$; on commit-to-files queries its candidate pool has lower recall than the conventional hybrid and the shared reranker adds nothing to either, at $n{=}18$. Margins measured on the re-partitioned ARB set do not survive the ledger that classifies how that set was used, and margins over hosted engines do not survive matching the quantity being measured. What survives is the protocol, together with a pilot whose audited seed and measured variance specify the study that could answer the title question.

\section{Matched baseline ladder}
\label{app:ladder}

\paragraph{Corpus and chunks.} Every rung operates on the same materialized snapshot as \system{} and the lexical comparators, chunked with the official ARB routine (one whole-file chunk plus one chunk per top-level symbol). Non-UTF-8 and binary blobs are skipped by the same guard \system{} uses.

\paragraph{Dense.} Chunks are embedded with \texttt{text-embedding-3-small} (1{,}536 dimensions) in token-aware batches (at most 200{,}000 tokens or 512 texts per request; texts above 8{,}000 tokens are truncated with the \texttt{cl100k\_base} tokenizer); vectors are cached keyed by model and content hash, so a chunk is embedded once regardless of how many rungs read it. Queries are embedded with the same model; similarity is cosine; a file's score is the maximum over its chunks; the top 50 files are returned.

\paragraph{Hybrid.} ARB's official BM25 chunk ranker over the same chunks, max-pooled to files, fused with the dense file ranking by reciprocal-rank fusion, $\mathrm{RRF}(f)=\sum_{r}1/(60+\mathrm{rank}_r(f))$ with equal weights. Nothing is tuned.

\paragraph{+ \system{}'s rerankers.} The top 50 fused files are narrowed to 30 with \system{}'s cross-encoder (\texttt{ms-marco-MiniLM-L-6-v2}, scored on the query and the first 4{,}000 characters of the file's best-matching chunk, its sigmoid blended at $\alpha{=}0.4$ with the fused score normalized by the top fused score, as in \system{}), then the top 20 are reordered by \system{}'s listwise reranker (\texttt{gpt-4o}, temperature 0, seed 1042, 280-character excerpts). The system prompt and the reply parser are imported from \system{}'s listwise-reranking module at the frozen revision.

\paragraph{+ \system{}'s expansion.} \system{}'s hypothetical-document expansion (\texttt{gpt-4o-mini}, temperature 0, seed 1042, 220-token reply) is applied under \system{}'s own gate (prose-like queries only) and the expansion text is appended to the dense query; BM25 sees the original query, as in \system{}. The prompt is imported from \system{}'s query-expansion module.

\paragraph{Hybrid + expansion (factorial cell).} For the factorial of Appendix~\ref{app:factorial}, a fifth conventional system applies the expansion to the hybrid's dense query and returns the fused ranking without learned reranking, so that expansion is held constant across the four cells.

\paragraph{Caching and latency.} LLM replies are cached keyed by model, prompt, and seed, so a repeat of a rung is bitwise identical and free. Reported latencies are wall-clock per query on a warm process excluding index construction, as for \system{}, and include hosted API round trips.

\paragraph{Listwise reranker system prompt (verbatim, shared with \system{}).}
\begin{quote}\footnotesize\ttfamily
You rank candidate source files by how directly each one answers a developer's request about a codebase.
You are given a request and a numbered list of candidates, each with its repository path and an excerpt.
Return the candidate numbers ordered best first, as a JSON array of integers, and nothing else. Example: [4,1,9,2]
Include every candidate number exactly once.
Judge by what the request actually asks for. If it asks which test covers some behaviour, a test file is the answer and the implementation is not. If it asks where something is implemented, the reverse holds. Prefer the file that would have to be opened or edited to satisfy the request over one that merely mentions the same words.
\end{quote}

\paragraph{Query-expansion system prompt (verbatim, shared with \system{}).}
\begin{quote}\footnotesize\ttfamily
You write short, plausible code snippets that would answer a developer's question about an unfamiliar codebase. Reply with code only: no prose, no explanation, no fences. Invent idiomatic function, class, and variable names for the language implied by the question. Being wrong about the specifics is fine; using the vocabulary real code would use is what matters. Keep it under 15 lines.
\end{quote}

\section{Candidate generation $\times$ reranking factorial}

\paragraph{Reading.} On issue queries (expansion set) the two factors are partial substitutes: \system{}'s candidates lead by $+0.188$ MRR before reranking and by $+0.041$ after it, because the rerankers add $+0.341$ to the conventional pool and $+0.193$ to \system{}'s. On the ARB partition the rerankers add $+0.008$ to conventional candidates. \paragraph{Re-indexing shift.} The independent corpus had to be re-indexed for its \system{} cells. Re-running the frozen configuration on the new index with an empty stage cache reproduced the confirmatory run's Recall@20 and BCY for every case but changed MRR on 5 of 18 cases ($+0.072$ \ci{+0.005}{+0.159} in aggregate); only 1 of 18 ordered top-20 lists and 7 of 18 top-20 sets were identical. The sources are re-embedding (which jitters similarities at the fifth decimal and reorders near-ties among $10^{5}$ chunks) and fresh seeded LLM calls for expansion and listwise reranking, which are not guaranteed identical across sessions. The confirmatory independent numbers are those of the original index; the factorial's within-index contrasts use the re-indexed cells, and the confirmatory-index contrast is shown alongside them in Table~\ref{tab:factcontrasts}.

\section{Development ablations and negative results}
\label{app:development}

\paragraph{Round-3 preregistered ablations (C1 development sets).} Exact vector scan replaced approximate (HNSW) search: $+0.020$ Recall@20 \ci{0.000}{0.063} on the ARB development set, with approximate search additionally implicated in run-to-run variance (Appendix~\ref{app:determinism}); accepted. Query expansion off versus on: expansion stayed on. Gemini embedding swap in place of \texttt{text-embedding-3-small}: MRR $-0.054$ \ci{-0.102}{-0.011}; rejected. File-level Okapi BM25 branch (whole-file BM25 as a seventh fused branch): the single approved configuration failed three preregistered gates (MRR interval floor $-0.050$ and BCY floor $-0.037$ against a $-0.01$ gate on each; warm median latency ratio $1.34$ against a $1.20$ gate) despite a non-negative Recall@20 delta and zero any-gold losses; rejected and shipped default-off. Two development findings moved code: review-comment queries retrieved the file the comment already quoted, so paths present in the query envelope are demoted after the cross-encoder (quoted-path demotion); and a global exclusion of generated protobuf sources had silently dropped a gold file, so agent-mode indexing now retains generated source under the existing size and binary guards.

\paragraph{Round-2 components, accepted on the ARB v2 pool (now C2).} Aligning the query-time embedding model with the index moved workflow-macro MRR from $0.055$ to $0.173$; reciprocal-rank fusion replaced max-normalized score fusion; the path-affinity branch made file paths searchable; the \texttt{ms-marco-MiniLM} cross-encoder at $k{=}30$, $\alpha{=}0.4$ moved MRR $0.176\to0.193$; hypothetical-document expansion moved held-out MRR $0.228\to0.241$ and Recall@20 $0.552\to0.579$; listwise reranking moved held-out MRR $0.241\to0.285$, Recall@5 $0.355\to0.419$, and BCY@8k $0.376\to0.446$. These are the decisions that make the round-3 ARB partition C2.

\paragraph{Round-2 ideas measured and rejected.} Recorded so that the negative space of the design is visible. Four of these looked like wins on the 75-case development split and lost on the 220-case held-out split; development differences under about $0.03$ were not trustworthy at that size, and run-to-run variance with an LLM in the loop was about $0.02$.
\begin{itemize}[leftmargin=1.2em]
\item \emph{File-evidence aggregation} (best chunk plus damped support from other chunks): Recall@20 $0.544\to0.467$ at $w{=}0.5$; many gold files match on exactly one chunk.
\item \emph{Deeper candidate pools} (50, 100, 150 per branch): MRR $0.197/0.195/0.194$; candidate supply was not the constraint.
\item \emph{Deeper rerank window} ($k{=}30, 60, 100$): Recall@20 $0.560/0.552/0.444$; the cross-encoder promotes plausible files from the tail.
\item \emph{Pure cross-encoder ordering} ($\alpha{=}1.0$): MRR $0.193\to0.154$, the worst configuration tested.
\item \emph{Larger code-aware reranker} (\texttt{bge-reranker-base}, 278M parameters): lost on every metric and ran $7\times$ slower ($21.3$ s vs.\ $2.9$ s).
\item \emph{Fusion weight rebalancing} (five configurations): defaults at or near the optimum; lexical-heavy clearly worse once embeddings were aligned.
\item \emph{Reverse-dependency branch} at a global weight: \texttt{edit2ripple} Recall@5 $0.238\to0.381$ but overall MRR $0.193\to0.163$; gated on query intent, the harm and the gain both vanished (held-out MRR $+0.004$, Recall@5 $-0.007$) because the listwise stage already promotes dependents.
\item \emph{File path prepended to rerank passages}: development Recall@5 $0.327\to0.333$, held-out $0.355\to0.346$.
\item \emph{Wider listwise pool} (20 to 40 candidates): $+0.016$ Recall@20 for $-0.016$ MRR and $-0.008$ Recall@5 and $+1.2$ s.
\item \emph{Cascade listwise} (second pass over the top 6 with 1{,}200-character excerpts): $+0.001$ MRR for $-0.036$ Recall@5 and $-0.017$ Recall@20.
\item \emph{Listwise window and excerpt tuning} ($k{=}12$, 700 characters): development Recall@5 $0.411$ vs.\ $0.391$, held-out $0.378$ vs.\ $0.419$.
\end{itemize}
The diagnostic that these attempts shared: on the held-out split $70.5\%$ of cases had a gold file in the top 20 and $54.1\%$ in the top 5, so the remaining gap was inside the reranker's window, and no change to coverage, fusion, pool size, or prompt shape moved it.

\section{Documentation track}
\label{app:docs}

\paragraph{Cases.} Forty DS-1000 problems (development subset, C1), eight each from NumPy, pandas, Matplotlib, scikit-learn, and TensorFlow, each annotated with a gold API identifier that a correct answer must name. Identifier hit is a case-insensitive substring match of the gold identifier against the scored text.

\paragraph{Arms.} \emph{Documentation engine} (hosted): library resolution followed by documentation retrieval; two modes were recorded, ``oracle'' (the library ID chosen by us) and ``quality-guided'' (the engine's own top-ranked library), both compacted to the 8{,}000-token budget. \emph{\system{}}: the frozen build indexing the same libraries' documentation sources, $k{=}5$ and $k{=}20$, compacted to the same budget. \emph{Synthesis engine} (hosted): its native answer mode, recorded once per case with its five cited source chunks; its raw-retrieval mode returned no sources during the recorded round. \emph{Reconstructed synthesis-engine retrieval}: the five source chunks extracted from each recorded response (mean 2{,}754 tokens per case), packed with the identical routine and budget. \emph{Frozen synthesis stage}: \texttt{gpt-5.4-mini}, temperature 0, 1{,}600 output tokens, the system prompt below, three repeats per arm. \emph{Control}: the same model and repeats with the control prompt and no retrieved context.

\section{Determinism}
\label{app:determinism}

\paragraph{Probes.} Eight ARB development queries repeated ten times each against the pre-freeze stack (mean exact top-10 rate $30.6\%$), with paired traces of every stage. Three sources were isolated: the listwise and expansion stages were uncached and unseeded; the fusion SQL broke ties by insertion order; and approximate nearest-neighbour search returned different neighbour sets under concurrent load. Fixes: total ordering in every SQL stage (score, then path, then chunk ID), single-flight sharing of concurrent identical hosted calls, an explicit LLM seed, and a persistent stage cache keyed by model, prompt, and seed. After the fixes: $100\%$ exact repeats in-process across two concurrent $8\times10$ packets and two 75-case repeats; a cold restart moved $7/8$ lists until the cache was warm, after which $8/8$ survived two restarts.

\paragraph{Embedding stability.} \texttt{text-embedding-3-small}: $N{=}20$ repeats of the same texts differed at the fifth decimal and never changed top-ten membership; Gemini embeddings were bitwise identical across repeats.

\paragraph{Like-for-like measures (Table~\ref{tab:determinism}, Figure~\ref{fig:determinism}).} Ten documentation cases $\times$ ten runs per engine, all $\binom{10}{2}\times 10=450$ run pairs. \emph{Retrieved set exact}: the set of retrieved units is identical (units: retrieved chunks for \system{} and the documentation engine; the set of cited URLs for the synthesis engine, whose retrieval is otherwise unobservable). \emph{Retrieved order exact}: the ordered list is identical. \emph{Context byte-exact}: the delivered text is identical. \emph{Identifier-hit agreement}: the scored outcome agrees across the pair. Because the observable units differ in granularity, the retrieved-set columns are reported per engine and are not used to rank engines against one another. A comparison of \system{}'s and the documentation engine's byte-exact context rate with the synthesis engine's byte-exact \emph{answer} rate measures different quantities and is the comparison Table~\ref{tab:determinism} replaces.

\section{Executable pilot}
\label{app:pilot}

\paragraph{Closed-tool seeding (replication of ARB).} ARB's seed intervention holds a closed-tool agent fixed and varies its initial context. We replicated it with \texttt{gpt-5.4-mini}, tools \texttt{list\_dir}/\texttt{grep}/\texttt{read\_file}/\texttt{submit}, and 40 paired development cases per arm, adding a seed from the pre-freeze \system{}. File-F1: no seed $0.046$; random files $0.013$; BM25 seed $0.093$; lexical seed $0.119$; \system{} seed $0.234$; oracle $0.858$. The \system{} seed beats no-seed by $+0.188$ \ci{0.055}{0.294} and BM25 by $+0.142$ \ci{0.059}{0.208}; against lexical the interval includes zero \ci{-0.002}{0.190}. Seeds change which files a frozen agent submits, ordered by seed quality, as ARB also found.

\paragraph{Protocol (preregistered before any run).} Tasks: the 62 round-3 SWE-bench Verified instances (C0). Agent: mini-SWE-agent 2.4.6, text-based action format, \texttt{gpt-5.4-mini}, official \texttt{x86\_64} instance images run under emulation on an Apple-silicon host. Conditions: \emph{no seed}; \emph{random} (five candidate files drawn with seed 1042 per instance, gold excluded); \emph{\system{}} (top five of the frozen build's recorded ranking); \emph{conventional} (top five of the full conventional stack's recorded ranking). Seed block: identical wording, up to five paths with the first 40 lines of each file at the base commit, capped at 3{,}000 tokens. Budgets: step limit 50 with a 2.0 USD cost cap; a tighter secondary budget was preregistered and not run because agents used 7--8 steps of 50. Outcome: verified repair under the official SWE-bench harness (v5.0.2) against the SWE-bench Verified release; secondary outcomes API cost, steps, and submission rate. Analysis: paired by instance; instance-cluster and repository-cluster bootstrap $95\%$ intervals (20{,}000 resamples, seed 1042); exact McNemar on discordant pairs. An interval including zero at $n{=}62$ is reported as unresolved. Repeats: two independent trajectories per instance and condition (496 trajectories), pooled as per-instance means.

\section{Hosted engine accounting}
\label{app:hosted}

\paragraph{Documentation engine.} Accessed through its public REST API with a project credential. Two retrieval modes were recorded (oracle library ID and quality-guided); the quality-guided mode is the fair comparison because it does not receive the gold library. Its retrieved documentation drifted across runs ($54\%$ retrieved-set exact), which is the engine's behaviour and not an artifact of our client.

\paragraph{Synthesis engine, documentation surface.} Accessed through its hosted API. The native answer mode was recorded once per case in round 3 with its cited sources; the raw-retrieval mode returned no sources during that round. Round 4 reconstructed the retrieved context from the recorded responses rather than issuing new calls, so the matched arm reflects the engine's round-3 retrieval exactly. Determinism probes (ten cases $\times$ ten runs) were issued in round 3.

\paragraph{Synthesis engine, repository surface.} Indexing the ARB development split requires 68 exact (repository, base commit) snapshots in the provider's account. Round 2 indexed 32 pairs through a sharded upload; whole-snapshot ingestion of the large repositories entered a ``syncing'' state that never reached a terminal status. Round 3 issued a minimal one-shard probe that remained syncing across a 40-minute deadline and a three-hour watch. Round 4 issued a fresh one-shard probe under a newly provisioned credential (which the account inventory shows resolves to the same account, with the earlier probes still syncing) that again timed out after 40 minutes. No repository query was ever scored against the engine, so no number is reported in either direction. We do not attribute the stall to the engine's design; it may be an account, quota, or ingestion-path issue that a different account would not encounter.

\paragraph{Credentials.} Hosted runs used project credentials supplied by the authors; none of the recorded artifacts contain them, and re-running the hosted arms requires the reader's own.

\section{Compute and cost}
\label{app:compute}

All round-4 experiments ran on one Apple-silicon workstation with a local PostgreSQL instance, using hosted APIs for embeddings and LLM stages. The matched ladder embedded $233.5$M new tokens across its runs (3{,}807 embedding requests, roughly \$4.70 at list price); its persistent embedding cache holds $1{,}440{,}990$ vectors ($11.9$ GB), and its LLM stage cache holds the listwise and expansion replies, so any rung, including the factorial's hybrid+expansion cell, can be re-executed bitwise without hosted calls. \system{}'s own stage cache for the frozen build is archived separately; the factorial's no-reranker cell reused its cached expansions. Re-indexing the 18 independent snapshots for the factorial embedded their chunks once more. The executable pilot ran 496 preregistered trajectories (4 conditions $\times$ 2 repeats $\times$ 62 instances) with four concurrent containerized workers under \texttt{amd64} emulation for a total API spend of \$10.97, plus 124 exploratory trajectories for the seed-interface check; harness evaluation ran the official SWE-bench images once per trajectory. The documentation matched arm reused recorded hosted responses and issued 120 frozen-synthesis calls. Round-3 costs (the \system{} runs, lexical comparators, determinism probes, and hosted documentation calls) are recorded in the archive's journals.
